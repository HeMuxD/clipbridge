# ClipBridge 开发指南

## 环境要求

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| Go | 1.22+ | 服务端 |
| .NET SDK | 8.0+ | Windows 客户端 |
| Android Studio | Hedgehog+ | Android 客户端 |
| JDK | 17 | Android 构建 |
| Nginx | 1.20+ | 反向代理（生产） |

## 一、服务端

### 本地运行

```bash
cd server

# 首次运行会自动生成配置缺失项并使用默认值
cp config.example.yaml config.yaml
# 编辑 config.yaml：至少改 public_base_url

# 拉依赖（首次需要网络访问代理）
go mod tidy

# 运行
go run ./cmd/clipbridge -config config.yaml
```

> SQLite 驱动使用 `modernc.org/sqlite`（纯 Go 实现）而非 `mattn/go-sqlite3`，
> 目的是让 `CGO_ENABLED=0` 的静态编译与交叉编译都能正常工作。
> 详见 `go.mod` 文件内的说明。

启动后终端会打印配对码：

```
============================================================
                    配对码（可多台设备重复使用）
                        48291307
              有效至 2026-09-28 22:10:33
============================================================
```

配对码在**有效期内可以反复使用** —— 手机、平板、笔记本依次用同一个码配对即可，
不必每加一台设备就重启服务端。

如果你连日志都不想翻，可以直接写死一个**固定码**，它永久有效：

```yaml
auth:
  pair_code: "13572468"     # 8 位数字
```

或者用环境变量 `CLIPBRIDGE_PAIR_CODE` 注入（`.env` 已是 600 权限，更适合放这类值）。

> ⚠️ 固定码 / 长期有效的码，安全前提是 `/api/pair` 的**按来源 IP 限流**
> （10 次/分钟）。8 位码有 1 亿种组合，按这个速率穷举一遍要约 19 年 ——
> 这正是"码可以放得久"的依据。**不要为了图快把限流去掉。**

换码方式：随机码重启服务端即换；固定码改配置后重启。

### 目录约定

运行时会创建：

```
server/
├── data/
│   ├── clipbridge.db      # SQLite 数据库
│   └── files/             # 上传的图片
└── config.yaml
```

### 常用参数

| 参数 | 说明 |
| --- | --- |
| `-config` | 配置文件路径，默认 `config.yaml` |
| `-version` | 打印版本号 |
| `-rotate-code` | 只打印当前配对码后退出。注意配对码是运行中进程的内存状态，独立进程无法真正换码 —— 换码请重启服务端 |

### 构建与部署

```bash
# 交叉编译到 Linux amd64（纯 Go 驱动，无需 C 工具链）
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -ldflags="-s -w" -o clipbridge ./cmd/clipbridge

# 或者直接用构建脚本
./scripts/build.sh linux

# 上传到服务器
scp clipbridge config.yaml user@server:/opt/clipbridge/
scp -r migrations user@server:/opt/clipbridge/
```

服务器上：

```bash
sudo useradd -r -s /usr/sbin/nologin clipbridge
sudo mkdir -p /var/lib/clipbridge/files /etc/clipbridge
sudo chown -R clipbridge:clipbridge /var/lib/clipbridge
sudo chown -R clipbridge:clipbridge /opt/clipbridge

# 生成并写入 JWT 密钥，避免重启后所有设备需要重新配对
echo "CLIPBRIDGE_JWT_SECRET=$(openssl rand -hex 32)" | sudo tee /etc/clipbridge/env
sudo chmod 600 /etc/clipbridge/env

sudo cp deploy/systemd/clipbridge.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now clipbridge
sudo journalctl -u clipbridge -n 50 --no-pager     # 查看配对码
```

Nginx：

```bash
sudo cp deploy/nginx/clipbridge.conf /etc/nginx/sites-available/clipbridge
# 编辑：把 clip.example.com 换成你的域名
sudo ln -s /etc/nginx/sites-available/clipbridge /etc/nginx/sites-enabled/

# 签发证书
sudo certbot certonly --nginx -d clip.example.com

sudo nginx -t && sudo systemctl reload nginx
```

### Docker 部署（推荐）

**一个镜像里同时包含 Go 二进制与 Nginx**，只需要一个容器。配置都在 `deploy/docker/`。

```bash
cd deploy/docker
cp .env.example .env
# 必填三项：
#   CLIPBRIDGE_SERVER_NAME      → 你的域名
#   CLIPBRIDGE_PUBLIC_BASE_URL  → https://<域名>:8443 （必须带端口）
#   CLIPBRIDGE_JWT_SECRET       → openssl rand -hex 32
docker compose up -d --build
docker compose logs -f clipbridge    # 配对码打印在这里
```

镜像结构：阶段一用 `golang:1.22-alpine` 编译出静态二进制；阶段二基于 `nginx:1.27-alpine`，
把二进制、建表 SQL 和 nginx 配置模板一起放进去。启动时由 `entrypoint.sh` 渲染 nginx 配置、
同时拉起两个进程并统一转发信号 —— 只有两个进程，不需要 supervisord/s6 那类进程管理器。

⚠️ **构建时 `apk add` 可能永久卡住**：基础镜像里的 apk 源指向 `dl-cdn.alpinelinux.org`，
国内实测会长时间没有进展（本项目真实踩过：community 的 APKINDEX 拉了数分钟一动不动，
而同一时刻宿主机的 curl 访问该地址却是正常的）。现在 Dockerfile 默认把 apk 源换成阿里云，
可用构建参数覆盖：

```bash
docker build --build-arg ALPINE_MIRROR=https://dl-cdn.alpinelinux.org/alpine ...   # 海外
```

在 compose 里对应的是 `.env` 的 `CLIPBRIDGE_ALPINE_MIRROR`。

容器内的进程布局：

| 进程 | 监听 | 说明 |
| --- | --- | --- |
| nginx | `8443`(HTTPS) / `8080`(HTTP) | 对外，TLS 终止 + 反代 |
| clipbridge | `127.0.0.1:18080` | 只监听回环，外部访问不到 |

#### 端口（家庭宽带的 80/443 已被封锁）

对外统一用 **8443**。`.env` 里的 `CLIPBRIDGE_HTTPS_PORT` 是**一个变量控制两侧**：

```yaml
ports:
  - "${CLIPBRIDGE_HTTPS_PORT:-8443}:${CLIPBRIDGE_HTTPS_PORT:-8443}"
environment:
  CLIPBRIDGE_HTTPS_PORT: "${CLIPBRIDGE_HTTPS_PORT:-8443}"
```

这样不会出现"容器里改了端口但宿主机映射没改"的错配。

⚠️ **`CLIPBRIDGE_PUBLIC_BASE_URL` 必须带上同一个端口号**（如 `https://nas.example.com:8443`）。
它是服务端拼接图片下载地址用的，少写端口客户端就会拿到打不开的 URL —— 表现为"文本能同步，图片一直下载失败"。

#### 证书

80/443 被封锁，所以只能用 **DNS-01** 验证。两种模式二选一。

**A) 容器外签发（默认）** —— 宿主机上装 acme.sh，签好后装进挂载目录：

```bash
acme.sh --issue --dns dns_cf -d <域名> --keylength ec-256
acme.sh --install-cert -d <域名> --ecc \
  --fullchain-file <CLIPBRIDGE_CERT_DIR>/fullchain.pem \
  --key-file       <CLIPBRIDGE_CERT_DIR>/privkey.pem \
  --reloadcmd      "docker exec clipbridge nginx -s reload"
```

容器内固定读 `/certs/fullchain.pem` 与 `/certs/privkey.pem`，
`CLIPBRIDGE_CERT_DIR` 就是宿主机上要挂进去的那个目录。

> ⚠️ `--reloadcmd` 用 `nginx -s reload` 而不是 `docker restart`：
> 证书目录是按**目录**挂载的，新文件立刻可见，热加载**不会断开现有连接**。
> 每次续期都重启容器会让手机端断连几秒，没必要。

**B) 容器内自动签发与续期** —— 宿主机上什么都不用装。设置 `CLIPBRIDGE_ACME_DOMAIN` 即启用：

```bash
# .env
CLIPBRIDGE_ACME_DOMAIN=nas.example.com     # ← 只加这一行就启用了
CLIPBRIDGE_ACME_EMAIL=admin@example.com
CF_Token=<Cloudflare API Token>
```

容器启动时会：

1. 从镜像源下载 acme.sh 与 DNS 钩子到数据卷（只在首次，之后复用；源可用 `CLIPBRIDGE_ACMESH_BASE` 覆盖）
2. 已有证书 → 直接启用 HTTPS；没有 → **先以明文 HTTP 起服务，后台签发**，
   签好后重新渲染配置并 `nginx -s reload` 切到 HTTPS（不阻塞启动）
3. 之后每 12 小时 `acme.sh --cron` 检查一次续期；证书内容真的变了才 reload
   （用内容摘要判断，不是看 mtime —— acme.sh 每次 cron 都会重写文件）

证书落在数据卷里：`/var/lib/clipbridge/certs/`，acme.sh 的状态与日志在同一卷的 `.acme/`。
取出来看：`docker exec clipbridge ls -l /var/lib/clipbridge/certs`。

| 关注点 | 说明 |
| --- | --- |
| 凭据从哪来 | 默认读容器环境变量（`.env` 里的 `CF_Token`）；想避免它出现在 `docker inspect` 里，用 `CLIPBRIDGE_ACME_ENV_FILE` + 挂载 `acme-credentials` 文件 |
| 别提交到 GitHub | `.env` 与 `acme-credentials` 都已在 `.gitignore` 里；推之前顺手 `grep -rn CF_Token` 确认一次 |
| 调试别烧配额 | 先设 `CLIPBRIDGE_ACME_STAGING=1` 走测试环境（生产环境同域名每周只能签 5 次） |
| 换服务商 | `CLIPBRIDGE_ACME_DNS=dns_ali` / `dns_dp` … 并提供该钩子需要的变量，钩子清单见 acme.sh 的 dnsapi 目录 |
| 强制 IPv4（默认开） | `CLIPBRIDGE_ACME_IPV4_ONLY=1` 会让 acme.sh 所有请求加 `--ipv4`。**别轻易关**：Docker 默认 bridge 没有 IPv6 出口，容器解析到 AAAA 后会先试 IPv6 并挂到超时，而 acme.sh 对 POST 请求不设响应超时 —— 一次丢包就永久卡死（本项目实测：`finalize` 那步挂着数分钟不动；强制 IPv4 后连续 5 次全部成功） |
| 失败会怎样 | 只影响它自己：容器照常跑、日志给出可操作原因、每 10 分钟自动重试。**不会因为证书问题把服务拖挂** |

**两种模式都没有证书时**：容器不会崩，只是降级成"仅监听明文 HTTP"并在日志里说明 ——
此时电脑端能调通，但 Android 9+ 拒绝明文，手机端连不上。

#### 容易踩的坑

1. `deploy/docker/config.yaml` **不能删**。compose 把它只读挂进容器；
   文件不存在时 Docker 会在宿主机上创建一个同名**目录**，容器启动随即失败
   （entrypoint 里专门加了检测，会直接给出这句提示而不是让你对着 nginx 报错发蒙）。
2. 镜像里的 nginx 反代目标是 `127.0.0.1:18080`（同一个容器内的回环），
   **不需要** Docker 网络，也**不需要**让任何外部进程去读数据卷里的图片：
   `/f/` 由 Go 进程自己提供（`internal/api/server.go` 的 `handleFile`）。
3. 构建上下文是**仓库根目录**（`context: ../..`），因此 `docker build` 要在仓库根执行：
   ```bash
   docker build -f deploy/docker/Dockerfile -t clipbridge:0.0.11 .
   ```
   根目录的 `.dockerignore` 已排掉 Android 构建产物、`server/data/` 等，别删它，否则镜像会大几十倍。

#### 更换域名

域名到期换新域名时，服务端要改的地方不多，但**有一个手工步骤不做就不会生效**。

**1) 先改 DNS 与凭据**

- 新域名加解析记录，指向 NAS（或 CNAME 到你 DDNS 用的记录名）
- DDNS 脚本里更新的记录名要同步改
- `CF_Token` 如果当初把 Zone Resources 限定成了「特定区域」，要把新域名加进去（或重建一个）

**2) 改 `.env` 里的三个变量**

```bash
CLIPBRIDGE_SERVER_NAME=新域名
CLIPBRIDGE_PUBLIC_BASE_URL=https://新域名:8443
CLIPBRIDGE_ACME_DOMAIN=新域名
```

**3) 🔴 必须手工清掉旧证书（关键一步）**

容器**不会**给新域名自动签发。原因在 `entrypoint.sh` 的 ACME 后台任务：

```sh
if ! cert_ready; then issue_cert; fi      # 只在「证书文件不存在」时才签发
while :; do ... run_acme --cron ... done  # 之后只续期，不签发新域名
```

而证书落在数据卷里的**固定路径**（`/var/lib/clipbridge/certs/fullchain.pem`），与域名无关 ——
旧域名的证书还在，`cert_ready` 就永远为真，新域名**一次都不会去签**；nginx 会继续拿旧证书，
客户端连新域名时报 TLS「域名不匹配」。

更麻烦的是：旧证书临近到期时，`acme.sh --cron` 会续期它，并按 acme.sh 记住的安装路径
**写回同一个文件** —— 就算你把新证书手工塞进去，也会被旧域名的覆盖。

所以清的时候要连 acme.sh 的状态一起清（代价只是重新注册一次 ACME 账号，几秒钟）：

```bash
docker exec clipbridge sh -c 'rm -rf /var/lib/clipbridge/certs /var/lib/clipbridge/.acme'
docker compose up -d          # 重建容器，让新的 .env 生效
```

> ⚠️ **别用 `docker compose down -v` 图省事。** `-v` 会把整个数据卷删掉，数据库一并没了。
> 而 `devices` 表里存着每台设备的 `token_hash`，服务端校验 Token 时既要验签名、又要查这张表
> （`s.store.GetDevice(deviceID, HashToken(token))`）—— 删卷等于所有 Token 失效，
> **每台设备都要重新配对**，历史内容也一起丢。为清个证书付这个代价太亏。

**4) 验证**

```bash
docker logs --tail 30 clipbridge        # 应出现「开始签发证书：新域名」
curl -s https://新域名:8443/healthz      # 应返回 ok
```

再用浏览器打开一次，确认证书是新域名的。

**5) 每台客户端改服务端地址**

| 端 | 怎么改 |
| --- | --- |
| Windows | 设置页直接改「服务端地址」并保存 —— 地址框没有锁定 |
| Android | 配对后地址框是**只读**的（设计如此，防止"看着还在用、其实已经连不上"）→ 先点「取消配对」，改完地址再用配对码重新配对 |

**不用重新配对**：Token 的签名内容是 `deviceID|过期时间`，用 `JWT_SECRET` 做 HMAC，**与域名无关**。
所以只要 `JWT_SECRET` 没变，老 Token 依然有效 —— 电脑端改完地址直接就能连上；
手机端虽然要走一次配对流程，但用的还是原来那个固定配对码。

**数据不受影响**：`clips` 表只存 `file_id`，图片下载 URL 是每次现拼的。
只有"历史记录里已经发出去的旧图片 URL"会失效 —— 那些都是临时缓存内容，无所谓。

> 想平滑过渡（旧域名还没到期）：可以让两个域名都指向 NAS —— nginx 的 `server_name`
> 支持写多个，acme.sh 也能一次签多个域名（`-d 旧 -d 新`）。但 `PUBLIC_BASE_URL` 只能填一个，
> 所以这只是"两个域名都能连"，不是完全双活。

#### 在 fnOS（飞牛 NAS）上部署

fnOS 用户**直接用上面这套标准 Docker 流程即可**，不需要打包成 FPK、也不需要把证书交给 fnOS 管。
下面是 fnOS 上特有的几个注意点。

**1) `docker compose` 必须显式指定 `DOCKER_CONFIG`**

fnOS 的家目录不可写，不指定会直接报：

```
mkdir /home/<用户名>/.docker: permission denied
```

解决（任选一个可写位置，之后所有 compose 命令都带上）：

```bash
# /vol1/<UID>/<用户名> 是 fnOS 上的用户空间目录，按自己的实际情况替换；
# 目录不存在就先 mkdir -p 一次。
DOCKER_CONFIG=/vol1/1000/<用户名>/Docker/.dockercli docker compose up -d --build
```

> `docker ps` / `docker images` / `docker logs` 这类**只读**命令不需要它。

**2) SSH 默认关闭，且别用 root**

SSH 要在【设置】里手动开启；登录用自己创建的管理员账户，`root` 会被拒
（`Permission denied (publickey,password)`）。密钥提前放进去，或用密码登录。

**3) FN Connect 和「统一网关」都帮不上 ClipBridge**

这是最容易白费时间的地方，先说结论：**该走 DDNS + 端口映射还是得走**，和在其他 Linux 上一样。

- fnOS 有个「统一网关」，用自己的 5666/5667 端口按 `/app/{应用名}` 反代到各应用；
  还有一个 FN Connect 远程访问服务，给你一个 `xxx.fnos.net` 的地址。
- 但两者都不能给 ClipBridge 这类**第三方原生客户端**用：
  - FN Connect 会把外部访问 302 转到飞牛自己的 Web 门户，背后是私有签名 API，
    **没有通用反代语义、不支持 WebSocket**；
  - 统一网关的 `/app/xxx` 路径要求 fnOS 账号登录，不带 token 直接返回 `invalid token`。

**4) 证书：建议继续用容器内 ACME（模式 B），省心**

fnOS 自带证书管理（【安全性】→【证书】）支持 Let's Encrypt + 多家 DNS + 自动续期，
看起来可以把证书统一交给它管，但有两个额外的摩擦点：

- 证书落在 `/usr/trim/var/trim_connect/ssls/{域名}/{时间戳}/`，属 `root`，
  而 fnOS 的管理员账户**没有 sudo**；
- **续期会换时间戳目录**（`1785209784` → `1785210189` 这样），挂固定路径会静默失效。

真要这么做，得配一个"找最新目录 → 复制到 `CLIPBRIDGE_CERT_DIR` → `nginx -s reload`"的同步任务，
平白多一个会坏的环节。所以除非你本来就在 fnOS 里管着一堆证书，否则**用模式 B 更合适**。

## 二、Windows 客户端

需要 **.NET SDK 8.0**（注意是 SDK，不是只有运行时）。

```bash
cd clients/windows/src

# 调试运行
dotnet run

# 发布单文件 exe（用户无需安装 .NET 运行时）
dotnet publish -c Release -r win-x64 --self-contained true \
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true
```

> `IncludeNativeLibrariesForSelfExtract=true` 不能省。WindowsDesktop 运行时带几个原生库
> （`wpfgfx_cor3.dll`、`PresentationNative_cor3.dll`、`D3DCompiler_47_cor3.dll`、
> `PenImc_cor3.dll`、`vcruntime140_cor3.dll`），不加这个参数它们会散落在 publish 目录里，
> 拿到的就不是单文件。加上之后 exe 会在首次启动时把它们解压到 `%TEMP%\.net\ClipBridge\`。

产物位于 `bin/Release/net8.0-windows/win-x64/publish/ClipBridge.exe`，单文件约 70 MB。

本机没有 SDK 时，可以直接下官方 zip 解压使用，**不需要管理员权限、不写系统目录**：

```bash
curl -L -o sdk.zip https://builds.dotnet.microsoft.com/dotnet/Sdk/8.0.425/dotnet-sdk-8.0.425-win-x64.zip
# 解压到某个目录后，让 dotnet 找到自己：
export DOTNET_ROOT="C:\\path\\to\\sdk"
export PATH="$DOTNET_ROOT:$PATH"
dotnet --info    # 应显示 8.0.425 + Microsoft.WindowsDesktop.App
```

### 运行期文件位置

| 内容 | 路径 |
| --- | --- |
| 配置 | `%APPDATA%\ClipBridge\settings.json` |
| Token（DPAPI 加密） | `%APPDATA%\ClipBridge\token.bin` |
| 日志 | `%APPDATA%\ClipBridge\logs\clipbridge-YYYYMMDD.log`（保留 7 天） |

排障先看日志：启动时会打印设备 ID、服务端地址、剪贴板监听与截图监控的启动结果。
托盘菜单里的「打开日志目录」直接跳过去。

### 使用流程

1. 运行 `ClipBridge.exe`，自动弹出设置窗口；
2. 填入服务端地址（如 `https://clip.example.com`）；
3. 填入服务端日志中的配对码，点「配对 / 重新配对」；
4. 配对成功后关闭窗口，程序驻留托盘；
5. 在「设置」中按需勾选开机自启、排除的应用等。

## 三、Android 客户端

> ⚠️ **开发前必读**：Android 10+ 起，后台应用无法读取剪贴板，且**没有任何权限可以申请**。
> AOSP `ClipboardService.clipboardAccessAllowed` 只对这几个身份放行**读**操作：
> 当前持有焦点的应用、默认输入法、SystemUI、ContentCapture 服务、Autofill 服务 ——
> **无障碍服务不在豁免名单里**。**写**操作不受此限（`OP_WRITE_CLIPBOARD` 直接放行）。
> 详见 `docs/可行性报告.md` 第 3.2 节。

### 架构：一个无障碍服务 + 一个连接引擎

| 组件 | 职责 |
| --- | --- |
| `ClipboardAccessibilityService` | **上行**：感知用户复制了什么；同时是长连接的保活载体之一（**零通知**） |
| `SyncEngine` | 连接持有者：心跳、指数退避重连、下行投递；用**引用计数**管理（无障碍服务 / 后台保护服务 / 分享入口都可能是持有者） |
| `ClipboardWriter` | 剪贴板写入（文本 + 图片 URI），以及"登记启动时既有内容" |
| `HashCache` | 防回环 + 同内容只同步一次 + 启动时登记历史内容 |
| `SyncService` | **后台保护**前台服务，默认开启（带一条静默通知） |
| `KeepAlive` / `KeepAliveReceiver` | 看门狗：`AlarmManager` 定期自检并把服务/连接拉回来 |
| `BootReceiver` | 开机自启，重启后自动恢复后台保护 |

### 上行为什么是两路

后台读剪贴板会被系统直接拒绝（`getPrimaryClip()` 返回 null），所以：

1. **先试读系统剪贴板** —— 部分 ROM、部分时机能读到，读到就直接用；
2. **读不到就回退**：监听 `TYPE_VIEW_TEXT_SELECTION_CHANGED` 记下用户选中的文本，
   当 `TYPE_VIEW_CLICKED` / `TYPE_VIEW_LONG_CLICKED` 命中「复制 / 剪切 / Copy / Cut」这类标签时，
   用刚才记下的选中内容上行。中文标签用包含匹配（"复制链接"也算），英文标签用精确匹配
   （否则 "cut" 会命中 "execute"）。

两路都拿不到时**宁可漏同步，也不伪造内容** —— 绝不能把用户没复制的东西发出去。

### 下行：静默写剪贴板，不发通知

- 文本：`setPrimaryClip(ClipData.newPlainText(...))`
- 图片：下载 → 存相册（Android 10+ 走 MediaStore，不需要存储权限）
  → 同时以 `content://` URI 写入剪贴板（部分系统对"从剪贴板读 URI"有限制，失败则只留相册）

顺序上必须**先登记 hash 再写剪贴板**，否则写入动作立刻被无障碍监听看到，形成 A→B→A 回环。

### 保活：两层结构

| 层 | 通知 | 作用 |
| --- | --- | --- |
| `ClipboardAccessibilityService` | **无** | 系统会保活它绑定的进程，这是最干净的持有者 |
| `SyncService`（后台保护） | 一条静默通知 | 前台身份，抗 ROM 掐后台 |

两者都通过 `SyncEngine.acquire()` 持有连接，引用计数归零才真正断开 —— 谁退出都不会立刻断。

后台保护靠这几点扛住清理：

1. `android:stopWithTask="false"` —— **划出最近任务时服务不被连带销毁**，这是"划掉后台照样同步"的关键；
2. `START_STICKY` —— 被系统回收后请求重建；
3. `onTaskRemoved` / `onDestroy` 里预约 `AlarmManager` 看门狗 —— 闹钟由系统持有、不随进程消亡，
   进程真被杀掉后它是唯一还能把服务叫回来的东西（每 5 分钟自检一次，见 `KeepAlive.WATCHDOG_INTERVAL_MS`）；
4. `BootReceiver` —— 手机重启后自动恢复；
5. **电池优化白名单 + 厂商自启动权限** —— 这两项必须由用户在系统里放开，App 只能引导，不能代替。

> ⚠️ **做不到的事**：用户在系统设置里"强行停止"之后，任何 App 都无法自启 —— 这是 Android 的设计。
> 另外 Android 15 起 `dataSync` 类型的前台服务有 6 小时/24 小时时长上限，且不允许由
> `BOOT_COMPLETED` 启动；本项目 `targetSdk = 34` 以规避时长限制，开机启动失败时由看门狗重试。

### 权限清单

```xml
<!-- 网络 -->
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />

<!-- 后台保护前台服务（Android 14+ 必须声明具体类型） -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />

<!-- 后台保护通知（Android 13+ 运行时申请）。没有它服务照跑，只是通知不可见 -->
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

<!-- 后台保护的恢复手段 -->
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
<uses-permission android:name="android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS" />
```

无障碍服务本身不需要 `uses-permission`，而是在 `<service>` 上声明
`android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"`，由用户在系统设置里授权。

## 四、端到端联调

### 1. 服务端健康检查

```bash
curl https://nas.example.com:8443/healthz
# {"status":"ok","online":0,"version":"0.0.11","time":...}
```

### 2. 模拟配对

```bash
curl -X POST https://nas.example.com:8443/api/pair \
  -H "Content-Type: application/json" \
  -d '{"pairCode":"482913","deviceId":"test-01","deviceName":"测试机","platform":"windows"}'
```

### 3. Windows ↔ Android 文本互测

1. Windows 上复制一段文字 → Android 的剪贴板应立刻就是这段文字（**不弹任何通知**，切到任意输入框直接粘贴即可验证）；
2. Android 上复制一段文字 → Windows 剪贴板应立即可粘贴（前提是已开启无障碍服务）；
3. 反复复测同一段内容，确认服务端日志**不会**重复广播（去重生效）。

### 4. 防回环验证（必做）

在 Windows 上复制文本 A，观察服务端日志：

```
内容已同步 from=win-xxx kind=text origin=clipboard delivered=1
```

**不应**出现第二条相同的 `内容已同步` 记录。若出现，说明防回环逻辑失效：

- Windows：检查 `SyncOrchestrator.OnRemoteClipReceived` 里 `_cache.Add(payload.Hash)`
  是否在写剪贴板**之前**执行（必须在之前）
- Android：检查 `SyncEngine.onText` 里 `HashCache.add(...)` 是否在 `ClipboardWriter.writeText`
  **之前**执行

### 5. 「只同步当前操作」验证

默认配置（`limits.offline_replay_seconds: 0`）下：

1. 关掉手机（或飞行模式）；
2. 在 Windows 上复制文本 B；
3. 恢复手机网络 → **不应**收到 B。服务端日志不会有 `补推离线内容`，
   因为内容根本没入队 —— 这就是"以往的复制操作不管"。
4. 把 `offline_replay_seconds` 改成 60 再跑一次 → 这次手机会收到 B，
   日志出现 `补推离线内容 deviceId=xxx count=1`。

## 五、故障排查

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| Windows 显示「未连接」 | 地址错误 / 证书问题 / 未配对 | 看日志目录；`curl /healthz` 是否通 |
| Android 端连不上 | 用了 `http://` | Android 9+ 禁止明文，必须 `https://`，且端口要对（默认 8443） |
| 文本能同步，图片一直下载失败 | `public_base_url` 少了端口号 | 必须是 `https://域名:8443` |
| 容器起来就退出，日志说找不到配置 | `./config.yaml` 被 Docker 建成了目录 | 确认 `deploy/docker/config.yaml` 存在（仓库里有） |
| 容器日志说"未找到证书" | 证书没装进 `CLIPBRIDGE_CERT_DIR` | 按上面的 A 模式命令装一次；或改用 B 模式让容器自己签 |
| A 模式下续期后不生效 | `--reloadcmd` 没配或用的 `docker restart` 失败 | 手动 `docker exec clipbridge nginx -s reload` |
| B 模式下日志停在"开始签发证书" | DNS 传播慢、令牌权限不足，**或 acme.sh 的请求挂住**（容器里默认会先试 IPv6，而 Docker bridge 没有 IPv6 出口；acme.sh 的 POST 又没有响应超时） | 先看 `docker exec clipbridge tail -50 /var/lib/clipbridge/.acme/acme.log`；若卡在某个 `curl` 上，确认 `CLIPBRIDGE_ACME_IPV4_ONLY` 没被设成 0 |
| B 模式下报"需要 API Token" | 设了 `CLIPBRIDGE_ACME_DOMAIN` 但没给凭据 | 在 `.env` 里补 `CF_Token=`，或用 `CLIPBRIDGE_ACME_ENV_FILE` 挂文件 |
| B 模式下报"指向的是一个【目录】" | 宿主机上那个凭据文件不存在，被 Docker 建成了目录 | `cp acme-credentials.example acme-credentials` 并填内容 |
| 签发一直失败、提示配额 | 试太多次把生产配额用完了 | 先设 `CLIPBRIDGE_ACME_STAGING=1` 验证流程，再改回 0 |
| `docker compose up --build` 卡在 `apk add` 不动 | 基础镜像里的 apk 源是 `dl-cdn.alpinelinux.org`，国内会挂住 | 确认 `CLIPBRIDGE_ALPINE_MIRROR` 为阿里云（默认即是），或手动指定别的镜像站 |
| `docker build` 报拉不到 `golang:1.22-alpine` | 镜像站偶发 502 | 重试即可；本项目实测 DaoCloud 有过瞬时 502，几秒后恢复正常 |
| 手机复制不同步 | 无障碍服务被 ROM 关掉了 | 打开 App 看首页的无障碍状态；或改用「分享 → ClipBridge」 |
| 手机收到内容但通知栏看不到 | 这是**预期行为** | 下行是静默写剪贴板，不发通知；图片可在相册 `Pictures/ClipBridge` 找到 |
| 复制内容不触发同步 | 前台应用在排除列表 | 检查 Windows 设置页「排除的应用」 |
| 同一内容被反复同步 | 防回环失效 | 检查 HashCache 的登记顺序（必须先登记再写剪贴板） |
| 服务端重启后要重新配对 | `CLIPBRIDGE_JWT_SECRET` 未持久化 | 写进 `.env` / `/etc/clipbridge/env` |
| 截图没同步 | 目录路径不对 / 文件未写完 | 查看日志；确认「监控系统截图目录」已勾选 |
| 启动后把旧截图发了一遍 | 不应发生 | 截图目录在启动时会做一次快照，旧文件一律忽略 |
| 上传报 413 | Nginx 与 Go 的大小限制不一致 | 对齐 `client_max_body_size` 与 `max_file_size` |

日志位置：

- Windows：`%APPDATA%\ClipBridge\logs\`
- Android：`adb logcat -s ClipBridgeA11y SyncEngine ClipClient`
- 服务端：`docker compose logs -f clipbridge` 或 `journalctl -u clipbridge -f`

## 六、开发约定

1. **协议优先**：任何消息格式变更必须先改 `shared/protocol/PROTOCOL.md`，再改实现；
2. **防回环是红线**：任何涉及"写剪贴板"的改动都必须回归验证回环，
   且**登记 hash 必须在写入之前**；
3. **新增字段一律可选**：保证旧客户端不会因新字段而解析失败；
4. **敏感信息不入日志**：文本内容只记录长度与哈希前缀，不记全文；
5. **"当前操作"语义**：客户端不得在启动时扫描/读取既有内容，
   服务端不得在默认配置下补推离线积压 —— 这是产品行为的基线，改动前先想清楚。
